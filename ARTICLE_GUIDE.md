# Article Guide

Этот файл фиксирует правила, по которым мы превращаем присланные тексты в учебные материалы для сайта.

## Цель

Каждая статья должна быть не просто копией исходного текста, а удобной учебной заметкой:

- быстро объясняет главную идею;
- сохраняет важные technical terms;
- раскладывает материал на понятные блоки;
- помогает повторить тему через вопросы;
- подходит для чтения с телефона и компьютера.

## Где хранить статьи

Русская версия CCNA-статей хранится здесь:

```text
articles/YYYY-MM/week-XX/NN-topic-name.md
```

Английская версия CCNA-статей хранится зеркально:

```text
articles-en/YYYY-MM/week-XX/NN-topic-name.md
quality-assurance-en/path/to/article.md
```

Пример:

```text
articles/2026-05/week-02/01-lan-vs-wan.md
articles-en/2026-05/week-02/01-lan-vs-wan.md
```

Имена файлов у русской и английской версии должны совпадать. Это важно для будущей локализации сайта и переключения языка.

## Языковые версии

Проект должен постепенно прийти к двум полноценным версиям материалов:

- Russian - основная версия для чтения сейчас;
- English - параллельная версия для будущего переключателя языка.
- English QA materials are stored in `quality-assurance-en/` and are not published until localization is added.

Для каждой новой CCNA-статьи нужно стремиться сохранять обе версии:

- если пользователь прислал текст на английском, сначала делаем русскую учебную статью в `articles/`, затем английскую версию в `articles-en/`;
- если пользователь прислал текст на русском, сначала делаем русскую статью в `articles/`, затем английскую версию в `articles-en/`;
- перевод не должен ломать структуру: заголовки, порядок секций, вопросы и ключевые термины должны оставаться сопоставимыми;
- английская версия должна быть естественной учебной заметкой, а не дословным машинным переводом русской версии;
- русская версия может оставлять networking terms на английском, если так понятнее и ближе к CCNA.

Пока полноценный `mkdocs-static-i18n` не включен, языковые версии хранятся в отдельных source-папках. Позже `scripts/sync_docs.py` и `mkdocs.yml` должны использовать эти папки для генерации `/ru/...` и `/en/...`.

## Структура статьи

Каждая статья следует базовому шаблону из `templates/article-note.md`.

Обязательные секции:

- `Summary` - короткое объяснение, о чем статья;
- `Key Points` - главные идеи списком;
- `Notes` - структурированный конспект;
- `Commands / Terms` - термины, команды, сокращения, протоколы;
- `Questions` - вопросы для самопроверки с ответами;
- `What To Review Later` - что стоит повторить позже.

Если в статье нет команд, секция `Commands / Terms` все равно остается, но заполняется терминами.

## Стиль русской версии

Русская статья должна звучать как понятный учебный конспект, а не как сухой перевод.

Правила:

- объяснять простым языком;
- сохранять важные network terms на английском: `switch`, `router`, `frame`, `packet`, `default gateway`, `VLAN`, `WAN`, `LAN`;
- при первом упоминании сложного термина давать простое объяснение;
- не перегружать один абзац несколькими идеями;
- использовать короткие подзаголовки;
- сохранять практический смысл: зачем это нужно в реальной сети;
- если в исходнике есть сценарий NetworkChuck Coffee, Castle Rysen Coffee или другой story context, сохранять его как учебный пример;
- добавлять выводы, которые помогают понять тему глубже, а не только пересказать исходник.

Пример хорошего подхода:

```text
Switch работает внутри LAN и принимает решения по MAC addresses. Он не "раздает интернет", а помогает локальным устройствам общаться эффективнее.
```

## Стиль английской версии

Английская версия должна быть самостоятельной readable study note.

Rules:

- keep the same learning structure as the Russian version;
- use natural English, not word-for-word translation;
- preserve networking terminology consistently;
- explain concepts plainly;
- keep examples and questions aligned with the Russian version;
- avoid adding new technical claims that are not present in the Russian version or source article unless they clarify an existing point.

## Что делать с исходным текстом

Исходный текст пользователя обычно более разговорный и длинный. Наша задача:

- выделить главную мысль;
- убрать лишние повторы;
- сохранить важные примеры;
- не потерять exam-relevant details;
- превратить рассказ в structured learning material;
- добавить вопросы и ответы для повторения.

Не нужно сохранять каждую фразу исходника. Нужно сохранить смысл и учебную ценность.

## Вопросы и ответы

В конце статьи должно быть несколько вопросов. Обычно достаточно 5-10, но для больших тем можно больше.

Хорошие вопросы проверяют:

- определения;
- различия между похожими понятиями;
- практический сценарий;
- причину, почему технология используется;
- ограничения или tradeoffs.

Ответ должен быть коротким, но достаточно ясным.

## Термины и команды

Секция `Commands / Terms` оформляется таблицей.

В нее попадают:

- protocol names;
- device roles;
- acronyms;
- Cisco commands;
- important numeric limits;
- standards;
- terms that likely appear in CCNA materials.

Пример:

```markdown
| Term | Meaning |
| --- | --- |
| LAN | Local Area Network; сеть внутри ограниченной области, например дома или офиса. |
| WAN | Wide Area Network; сеть для связи на больших расстояниях, часто через internet или provider network. |
```

## Проверка перед сохранением

Перед завершением новой статьи проверить:

- файл лежит в правильной папке недели;
- номер файла идет по порядку;
- заголовок понятный;
- структура соответствует шаблону;
- есть `Summary`, `Key Points`, `Notes`, `Commands / Terms`, `Questions`, `What To Review Later`;
- русская и английская версии лежат зеркально, если перевод уже сделан;
- `mkdocs.yml` обновлен, если статья должна появиться в навигации;
- `python scripts/sync_docs.py` и `mkdocs build --strict` проходят перед деплоем.

## Коммиты

После важных изменений нужно делать локальный git commit.

Обычно отдельный commit подходит для:

- добавления пачки статей;
- добавления переводов;
- изменения структуры сайта;
- изменения правил или шаблонов.
