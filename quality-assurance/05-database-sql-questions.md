## Summary

Материал помогает повторить SQL, реляционные и нереляционные базы данных, проверку консистентности данных, транзакции, подготовку тестовых данных и backend verification.

## Key Points

- Реляционные БД хранят данные в таблицах и используют ключи, constraints и SQL для связей и проверок.
- NoSQL базы выбирают для гибкой схемы, cache, поиска, логов, высокой нагрузки или распределенных данных.
- QA часто проверяет не только UI/API, но и последствия в БД: баланс, транзакции, историю действий и консистентность.
- `JOIN` объединяет таблицы по связи, а `UNION` объединяет результаты запросов в один список строк.
- Primary key, foreign key, unique key и index помогают понимать структуру данных и искать причины багов.

## Notes

## 1. Отличия реляционных БД от других. Названия и примеры

**Реляционная база данных** хранит данные в таблицах. Таблицы состоят из строк и колонок, а связи между таблицами задаются через ключи: primary key и foreign key. Для работы обычно используется SQL.

Примеры реляционных БД:

- **PostgreSQL**
- **MySQL**
- **Microsoft SQL Server**
- **Oracle Database**
- **SQLite**

Пример: в poker platform могут быть таблицы `users`, `tables`, `hands`, `transactions`, `balances`. Пользователь связан с балансом, игровой рукой, транзакциями и сессиями через ключи.

**Нереляционные базы данных** не всегда используют таблицы и строгую схему. Они могут хранить данные как документы, key-value пары, графы или колонки.

Примеры нереляционных БД:

- **MongoDB** - document database, хранит JSON-like документы.
- **Redis** - key-value storage, часто используется для кеша, сессий, быстрых временных данных.
- **Cassandra** - wide-column database, подходит для больших распределенных нагрузок.
- **Neo4j** - graph database, хорошо подходит для связей между объектами.
- **Elasticsearch** - search/index database, часто используют для поиска и логов.

Главные отличия:

- В реляционных БД данные обычно структурированы в таблицах, в NoSQL структура может быть гибче.
- В реляционных БД связи и целостность данных контролируются через ключи и constraints.
- SQL хорошо подходит для сложных запросов, `JOIN`, агрегаций и отчетов.
- NoSQL часто выбирают для гибкой схемы, высокой скорости записи, кеша, распределенных данных или поиска.

Для QA важно понимать, где хранятся какие данные. Например, основной баланс игрока может быть в PostgreSQL, сессия - в Redis, а логи действий - в Elasticsearch.

## 2. Основные SQL-запросы. JOIN и UNION, их отличия

Основные SQL-команды:

```sql
SELECT * FROM users;
```

Получить данные из таблицы.

```sql
SELECT id, email, status
FROM users
WHERE status = 'active';
```

Получить только нужные колонки и строки по условию.

```sql
INSERT INTO users (email, status)
VALUES ('test@example.com', 'active');
```

Добавить новую запись.

```sql
UPDATE users
SET status = 'blocked'
WHERE id = 10;
```

Обновить запись.

```sql
DELETE FROM users
WHERE id = 10;
```

Удалить запись.

```sql
SELECT *
FROM transactions
ORDER BY created_at DESC
LIMIT 10;
```

Сортировка и ограничение количества строк.

```sql
SELECT user_id, COUNT(*) AS transaction_count
FROM transactions
GROUP BY user_id;
```

Группировка и агрегация.

### JOIN

**JOIN** объединяет данные из нескольких таблиц по связанному полю.

Пример:

```sql
SELECT u.id, u.email, b.amount
FROM users u
JOIN balances b ON b.user_id = u.id
WHERE u.id = 10;
```

Так можно получить пользователя и его баланс.

Основные виды JOIN:

- **INNER JOIN** - возвращает только строки, где есть совпадение в обеих таблицах.
- **LEFT JOIN** - возвращает все строки из левой таблицы и совпадения из правой. Если совпадения нет, будут `NULL`.
- **RIGHT JOIN** - возвращает все строки из правой таблицы и совпадения из левой.
- **FULL JOIN** - возвращает все строки из обеих таблиц, даже если совпадений нет.

Пример LEFT JOIN:

```sql
SELECT u.id, u.email, b.amount
FROM users u
LEFT JOIN balances b ON b.user_id = u.id;
```

Этот запрос покажет всех пользователей, даже если у кого-то еще нет записи в `balances`.

### UNION

**UNION** объединяет результаты двух или нескольких `SELECT` в один список строк.

Пример:

```sql
SELECT user_id, amount, created_at
FROM deposits
UNION
SELECT user_id, amount, created_at
FROM withdrawals;
```

`UNION` убирает дубликаты. Если нужно сохранить дубликаты, используют `UNION ALL`.

```sql
SELECT user_id, amount
FROM deposits
UNION ALL
SELECT user_id, amount
FROM withdrawals;
```

### Отличие JOIN от UNION

- **JOIN** добавляет колонки рядом, объединяя таблицы горизонтально по связи.
- **UNION** добавляет строки вниз, объединяя результаты вертикально.

Просто:

- `JOIN` - "соедини пользователя с его балансом".
- `UNION` - "покажи депозиты и выводы одним списком".

## 3. Ключи. Primary key и составные ключи

**Ключи** нужны, чтобы идентифицировать записи и связывать таблицы между собой.

**Primary key** - главный уникальный идентификатор строки в таблице.

Особенности primary key:

- уникальный;
- не может быть `NULL`;
- обычно один на таблицу;
- часто это `id`.

Пример:

```sql
CREATE TABLE users (
  id INT PRIMARY KEY,
  email VARCHAR(255) NOT NULL
);
```

**Foreign key** - внешний ключ. Он связывает одну таблицу с другой.

Пример:

```sql
CREATE TABLE balances (
  id INT PRIMARY KEY,
  user_id INT REFERENCES users(id),
  amount NUMERIC(10, 2) NOT NULL
);
```

Здесь `balances.user_id` ссылается на `users.id`.

**Composite key / составной ключ** - ключ, который состоит из нескольких колонок.

Пример:

```sql
CREATE TABLE table_players (
  table_id INT,
  user_id INT,
  PRIMARY KEY (table_id, user_id)
);
```

Такой ключ означает, что комбинация `table_id + user_id` должна быть уникальной. Один и тот же пользователь не может быть дважды добавлен за один и тот же стол, но может быть за разными столами, если бизнес-логика это разрешает.

Отличие:

- обычный primary key часто состоит из одной колонки, например `id`;
- составной primary key состоит из двух или более колонок;
- оба варианта обеспечивают уникальность, но составной ключ уникализирует именно комбинацию значений.

Также часто встречаются:

- **Unique key** - поле или комбинация полей должны быть уникальными, например `email`.
- **Index** - ускоряет поиск, фильтрацию и join, но сам по себе не всегда означает уникальность.

## 4. Функции и методы в SQL

В SQL часто используют встроенные функции для обработки данных, агрегации, строк, дат и чисел.

### Агрегатные функции

Работают по группе строк:

```sql
SELECT COUNT(*) FROM users;
SELECT SUM(amount) FROM transactions WHERE user_id = 10;
SELECT AVG(amount) FROM transactions;
SELECT MIN(amount), MAX(amount) FROM transactions;
```

Частые функции:

- `COUNT()` - количество записей.
- `SUM()` - сумма.
- `AVG()` - среднее значение.
- `MIN()` - минимальное значение.
- `MAX()` - максимальное значение.

### Строковые функции

```sql
SELECT LOWER(email) FROM users;
SELECT UPPER(status) FROM users;
SELECT LENGTH(email) FROM users;
```

Частые функции:

- `LOWER()` - привести к нижнему регистру.
- `UPPER()` - привести к верхнему регистру.
- `LENGTH()` - длина строки.
- `CONCAT()` - склеить строки.

### Функции дат и времени

```sql
SELECT NOW();
SELECT CURRENT_DATE;
```

Часто используют для проверки `created_at`, `updated_at`, времени транзакций и игровых событий.

### Условные выражения

```sql
SELECT
  user_id,
  amount,
  CASE
    WHEN amount > 0 THEN 'positive'
    WHEN amount < 0 THEN 'negative'
    ELSE 'zero'
  END AS amount_type
FROM transactions;
```

`CASE WHEN` помогает вывести разные значения в зависимости от условия.

### HAVING

`WHERE` фильтрует строки до группировки, а `HAVING` фильтрует результат после `GROUP BY`.

```sql
SELECT user_id, COUNT(*) AS transaction_count
FROM transactions
GROUP BY user_id
HAVING COUNT(*) > 5;
```

Для QA это полезно, например, чтобы найти пользователей с большим количеством транзакций или проверить, не создались ли дубликаты.

## 5. Хранимые процедуры: зачем нужны, преимущества и недостатки

**Хранимая процедура / stored procedure** - это заранее сохраненный набор SQL-команд на стороне базы данных. Ее можно вызвать по имени и передать параметры.

Пример условно:

```sql
CALL update_user_balance(10, 100);
```

Зачем нужны хранимые процедуры:

- выполнять сложную бизнес-логику ближе к данным;
- переиспользовать один и тот же набор SQL-команд;
- уменьшить дублирование логики в приложениях;
- выполнять несколько операций как одну логическую операцию;
- ограничить прямой доступ к таблицам и дать доступ только к процедурам.

Преимущества:

- быстрее выполнять сложные операции рядом с данными;
- меньше дублирования SQL в приложении;
- можно централизовать важную бизнес-логику;
- можно улучшить безопасность через ограничение прав;
- удобно для batch operations, отчетов, миграций, расчетов.

Недостатки:

- бизнес-логика становится спрятанной в БД, ее сложнее читать и ревьюить;
- сложнее версионировать и деплоить, если процесс не настроен;
- сложнее тестировать, чем обычный application code;
- может быть зависимость от конкретной БД, например PostgreSQL или Oracle;
- если процедур слишком много, приложение становится труднее поддерживать.

Для QA важно понимать, что баг может быть не только в backend code, но и в stored procedure. Например, если баланс после ставки считается неверно, проблема может быть в процедуре, которая обновляет `balances` и `transactions`.

## 6. Отличия работы в реляционной БД и остальных

В реляционной БД QA чаще работает через SQL и проверяет:

- таблицы;
- связи между таблицами;
- primary/foreign keys;
- constraints;
- транзакции;
- JOIN-запросы;
- консистентность данных.

Пример проверки в реляционной БД:

```sql
SELECT u.email, b.amount, t.amount AS last_transaction
FROM users u
JOIN balances b ON b.user_id = u.id
JOIN transactions t ON t.user_id = u.id
WHERE u.id = 10
ORDER BY t.created_at DESC;
```

Так можно проверить пользователя, баланс и последние транзакции.

В нереляционной БД подход зависит от типа БД:

- В **MongoDB** QA проверяет документы, вложенные структуры, поля JSON, индексы и фильтры.
- В **Redis** часто проверяют ключи, значения, TTL, кеш, сессии, временные данные.
- В **Elasticsearch** проверяют индексы, поиск, фильтры, логи и корректность проиндексированных данных.
- В **Cassandra** часто смотрят распределенные данные, скорость записи, ключи партиционирования.

Главные отличия в работе:

- В SQL-БД данные обычно нормализованы и разбиты по связанным таблицам.
- В NoSQL данные часто денормализованы и могут храниться целым документом.
- В SQL-БД удобно делать сложные `JOIN` и проверки связей.
- В NoSQL часто быстрее получить готовый документ, но сложнее делать сложные связи.
- В SQL-БД схема обычно строже, в NoSQL часто гибче.
- Для SQL чаще пишем SQL-запросы, для NoSQL используем свой query language или команды конкретной БД.

Пример из продукта:

- PostgreSQL может хранить пользователей, балансы, транзакции и историю раздач.
- Redis может хранить активные сессии, временное состояние стола или locks.
- Elasticsearch может хранить логи действий и ошибок для анализа багов.

Хороший ответ на интервью:

"В реляционной БД я обычно проверяю данные через SQL: таблицы, связи, ключи, constraints, транзакции и консистентность. Например, могу проверить, что после действия игрока корректно обновились баланс, транзакция и история hand. В NoSQL подход зависит от типа базы: в MongoDB смотрю документы, в Redis - ключи и TTL, в Elasticsearch - логи и индексы. Главное отличие в том, что реляционные БД строже структурированы и удобны для связей через JOIN, а NoSQL чаще используют для гибкой схемы, кеша, поиска или высокой нагрузки."

## Commands / Terms

| Term | Meaning |
| --- | --- |
| SQL | Язык запросов для работы с реляционными базами данных. |
| Primary key | Уникальный идентификатор строки в таблице. |
| Foreign key | Поле, которое связывает запись с другой таблицей. |
| Composite key | Ключ из нескольких колонок, уникализирующий их комбинацию. |
| JOIN | Объединение таблиц по связанному полю. |
| UNION | Объединение результатов нескольких `SELECT` в один список строк. |
| Constraint | Ограничение данных в БД, например `NOT NULL`, `UNIQUE` или foreign key. |
| Stored procedure | Сохраненный набор SQL-команд, который выполняется на стороне БД. |
| TTL | Time to live; срок жизни ключа или записи, часто в cache/Redis. |
