# Real-Time и Client-Server Questions

Source: Interview Prep

Related plan item: QA interview preparation

## Summary

Материал разбирает client-server architecture, real-time systems, WebSocket, синхронизацию между клиентами, reconnect, error handling, latency, race conditions и консистентность состояния.

Это ключевая тема для вакансии, потому что poker platform - это live real-time продукт с несколькими клиентами, игровым состоянием, таймерами, действиями игроков, reconnect и риском рассинхронизации.

## Key Points

- В real-time продукте сервер должен быть source of truth для бизнес-логики, баланса, игровых правил и результата hand.
- REST API удобен для команд и CRUD, а WebSocket или похожий transport нужен для быстрых server-to-client событий.
- QA проверяет полный flow: client request, backend processing, DB/logs, real-time events и обновление UI на других клиентах.
- Главные риски real-time систем: latency, disconnect, missed events, duplicate events, out-of-order events, race conditions и stale data.
- После reconnect клиент должен получить актуальный server snapshot, а не доверять старому локальному состоянию.

## Notes

## 1. Виды client-server архитектуры. Плюсы и минусы

**Client-server architecture** - это модель, где клиент отправляет запросы, а сервер обрабатывает их, хранит данные, выполняет бизнес-логику и возвращает ответ.

В poker platform клиентом может быть mobile app, desktop app или web client, а сервер отвечает за авторизацию, игровые столы, действия игроков, баланс, историю рук, транзакции и синхронизацию состояния.

### 1. Thin client / тонкий клиент

Вся основная логика находится на сервере. Клиент в основном отображает данные и отправляет действия пользователя.

Примеры:

- web app, где основная логика на backend;
- mobile client, который только отображает table state и отправляет actions: call, fold, raise.

Плюсы:

- меньше бизнес-логики на клиенте;
- проще контролировать правила игры на сервере;
- меньше риск cheating/manipulation на клиенте;
- легче обновлять бизнес-логику без обновления приложения;
- единая логика для mobile, desktop и web.

Минусы:

- сильная зависимость от сети;
- выше нагрузка на сервер;
- при latency пользователь может видеть задержки;
- offline режим почти невозможен для real-time продукта.

Для poker platform это обычно правильный подход: критичная игровая логика, баланс и результат hand должны контролироваться сервером.

### 2. Thick client / fat client / толстый клиент

Часть логики находится на клиенте. Клиент может сам выполнять расчеты, валидации, кешировать данные и иногда работать без постоянного обращения к серверу.

Плюсы:

- быстрее реакция UI;
- меньше запросов к серверу;
- можно лучше поддерживать offline/poor network scenarios;
- часть работы переносится с сервера на клиент.

Минусы:

- сложнее поддерживать одинаковую логику на разных клиентах;
- выше риск рассинхронизации;
- сложнее обновлять логику, особенно в mobile app;
- нельзя доверять клиенту в критичных действиях;
- больше рисков безопасности.

Для poker platform толстый клиент может использоваться для UI, анимаций, локального отображения таймера, предварительной валидации. Но финальное решение по действиям игрока должен принимать сервер.

### 3. Two-tier architecture

Клиент напрямую общается с сервером или базой данных. В классическом варианте есть client + database/server.

Плюсы:

- простая архитектура;
- меньше компонентов;
- подходит для небольших внутренних систем.

Минусы:

- плохо масштабируется;
- сложнее обеспечить безопасность;
- клиент может получить слишком прямой доступ к данным;
- не подходит для сложных публичных high-load продуктов.

Для live poker platform такой подход обычно не подходит, потому что нужны backend services, auth, validation, logging, scaling и защита данных.

### 4. Three-tier architecture

Есть три уровня:

- client / presentation layer;
- application server / business logic layer;
- database / data layer.

Плюсы:

- четкое разделение ответственности;
- бизнес-логика находится на сервере;
- лучше безопасность;
- проще масштабировать backend отдельно от БД;
- удобно тестировать API и интеграции.

Минусы:

- больше компонентов;
- сложнее настройка окружений;
- возможны ошибки интеграции между слоями;
- нужно мониторить больше мест: client, API, backend, DB.

Это один из самых типичных вариантов для web/mobile продуктов.

### 5. Microservices architecture

Backend состоит из нескольких отдельных сервисов, каждый отвечает за свою область.

Пример для poker platform:

- auth service;
- user profile service;
- table/game service;
- wallet/balance service;
- payment service;
- notification service;
- logging/analytics service.

Плюсы:

- сервисы можно масштабировать независимо;
- команды могут работать над разными сервисами;
- проще изолировать доменную логику;
- отказ одного сервиса не всегда ломает весь продукт;
- удобно для high-load систем.

Минусы:

- сложнее интеграционное тестирование;
- больше сетевых взаимодействий;
- возможны distributed failures;
- сложнее tracing/logging;
- могут быть проблемы eventual consistency;
- сложнее локальные окружения.

Для QA важно проверять не только один endpoint, но и цепочку: client -> API gateway -> game service -> wallet service -> DB/logs.

### 6. Monolith architecture

Вся backend-логика находится в одном приложении.

Плюсы:

- проще разрабатывать и запускать на старте;
- проще локальное тестирование;
- меньше сетевых вызовов между компонентами;
- легче отследить flow внутри одной системы.

Минусы:

- со временем кодовая база может стать сложной;
- сложнее масштабировать отдельные части;
- изменение одного модуля может влиять на весь продукт;
- деплой часто затрагивает всю систему.

Монолит не обязательно плохой. Для многих продуктов это нормальный старт. Но для live high-load платформы со временем часто появляются отдельные сервисы.

### 7. Request-response architecture

Классическая модель: клиент отправляет request, сервер возвращает response.

Пример:

- `GET /tables/{id}` - получить состояние стола;
- `POST /tables/{id}/actions` - отправить действие игрока.

Плюсы:

- просто тестировать;
- хорошо подходит для REST API;
- понятные status codes и responses;
- удобно логировать.

Минусы:

- сервер сам не может мгновенно отправить обновление клиенту;
- для real-time приходится использовать polling или дополнительные механизмы;
- не идеально для быстрых событий за игровым столом.

### 8. Real-time communication: WebSocket / Socket connection

Клиент и сервер держат постоянное соединение. Сервер может сам отправлять события клиенту.

Примеры событий:

- игрок сделал raise;
- началась новая hand;
- обновился pot;
- истек таймер;
- игрок disconnected/reconnected.

Плюсы:

- подходит для real-time обновлений;
- меньше задержка, чем при polling;
- сервер может push-ить события всем клиентам;
- хорошо подходит для multiplayer games.

Минусы:

- сложнее тестировать;
- нужно проверять reconnect;
- возможны missed/duplicate/out-of-order events;
- сложнее логирование и debugging;
- нужно контролировать состояние соединения.

Для poker platform WebSocket или похожий real-time transport очень важен, потому что все игроки за столом должны видеть одинаковое состояние почти одновременно.

### 9. Polling и long polling

**Polling** - клиент регулярно спрашивает сервер: "Есть обновления?"

**Long polling** - клиент отправляет request, а сервер держит его открытым до появления события или timeout.

Плюсы polling:

- просто реализовать и тестировать;
- работает поверх обычного HTTP;
- легче отлаживать.

Минусы polling:

- лишняя нагрузка на сервер;
- задержка зависит от интервала;
- не идеально для real-time.

Плюсы long polling:

- ближе к real-time;
- не требует WebSocket.

Минусы long polling:

- сложнее обычного polling;
- все равно менее удобно, чем WebSocket для активной multiplayer-сессии.

## 2. Вопросы, которые могут спросить по client-server, sync, reconnects, error handling

### Базовые client-server вопросы

**Что такое client-server architecture?**

Client-server architecture - это модель, где клиент отправляет запросы, а сервер обрабатывает их, выполняет бизнес-логику, работает с данными и возвращает ответ. В poker platform клиент показывает стол и действия игрока, а сервер контролирует правила игры, баланс, состояние hand и синхронизацию.

**Что происходит, когда клиент отправляет request на сервер?**

Клиент формирует request с method, URL, headers и body/params. Сервер принимает request, проверяет auth, валидирует данные, выполняет бизнес-логику, при необходимости обращается к БД или другим сервисам и возвращает response со status code и body.

**Чем frontend/client отличается от backend/server?**

Frontend/client отвечает за UI, ввод пользователя и отображение данных. Backend/server отвечает за бизнес-логику, безопасность, хранение данных, интеграции и принятие финальных решений. В real-time игре клиент может показывать действие, но сервер должен подтверждать, что оно валидно.

**Почему нельзя доверять данным, которые приходят с клиента?**

Клиент можно изменить, перехватить request или отправить его вручную через Postman/скрипт. Поэтому сервер обязан заново проверять права, формат данных, баланс, состояние игры, таймеры и доступность action.

**Какие данные и проверки должны быть на сервере, а какие могут быть на клиенте?**

На клиенте можно делать предварительную валидацию для удобства пользователя: пустые поля, формат, disable кнопки. На сервере обязательно должны быть критичные проверки: auth, permissions, balance, game state, allowed actions, duplicate requests и business rules.

**Что такое request и response?**

Request - это запрос клиента к серверу: method, URL, headers, params, body. Response - ответ сервера: status code, headers и body. QA проверяет оба: что клиент отправил и что сервер вернул.

**Что такое headers, body, query params, path params?**

Headers содержат служебную информацию: auth token, content type, request id. Body содержит основные данные для POST/PUT/PATCH. Query params идут после `?` и часто используются для фильтров/пагинации. Path params являются частью URL, например `/tables/{tableId}`.

**Чем REST API отличается от WebSocket?**

REST API обычно работает по request-response модели: клиент отправил запрос, сервер ответил. WebSocket держит постоянное соединение, и сервер может сам отправлять события клиенту. REST удобен для CRUD и команд, WebSocket лучше для real-time обновлений.

**Что такое API gateway?**

API gateway - это входная точка для клиентских запросов к backend. Он может заниматься routing, auth, rate limiting, logging, aggregation и передачей request в нужный сервис.

**Что такое load balancer и зачем он нужен?**

Load balancer распределяет traffic между несколькими серверами, чтобы система выдерживала нагрузку и оставалась доступной, если один instance упал. Для high-load poker platform это важно, потому что много пользователей могут играть одновременно.

### Вопросы по real-time systems

**Что такое real-time система?**

Real-time система быстро передает и обновляет данные, чтобы пользователи видели актуальное состояние почти сразу. В poker это состояние стола, действия игроков, таймеры, pot и результат hand.

**Чем real-time отличается от обычного request-response API?**

В обычном API клиент сам запрашивает данные. В real-time системе сервер может отправлять обновления клиентам сразу после события, например через WebSocket. Поэтому важны latency, порядок событий, reconnect и синхронизация.

**Как клиент получает обновления от сервера в real-time?**

Обычно через WebSocket, push/event stream, long polling или polling. Для live game чаще используют WebSocket, потому что сервер может быстро отправлять события всем игрокам за столом.

**Что лучше для live game: polling или WebSocket? Почему?**

WebSocket обычно лучше, потому что дает постоянное соединение и быстрые server-to-client события. Polling проще, но создает лишнюю нагрузку и задержку между обновлениями.

**Какие проблемы бывают в real-time системах?**

Latency, потеря соединения, missed events, duplicate events, out-of-order events, race conditions, stale data, reconnect issues и рассинхронизация клиентов. QA должен проверять не только happy path, но и нестабильные сетевые условия.

**Что такое latency и как она влияет на пользователя?**

Latency - задержка между действием и реакцией системы. В poker высокая latency может привести к тому, что игрок поздно увидит ход другого игрока, таймер или обновление pot.

**Что такое race condition?**

Race condition - ситуация, когда результат зависит от порядка выполнения нескольких параллельных действий. Например, два события приходят почти одновременно, и система неправильно определяет active player или применяет action не в том порядке.

**Что такое stale data?**

Stale data - устаревшие данные на клиенте. Например, клиент показывает старый balance или старое состояние стола, хотя на сервере оно уже изменилось.

**Что такое eventual consistency?**

Eventual consistency - модель, где данные в разных частях системы могут быть временно несогласованными, но через некоторое время приходят к одному состоянию. В QA важно понимать, где допустима небольшая задержка, а где нужна строгая консистентность.

**Как проверить, что два клиента видят одинаковое состояние стола?**

Открыть один table под разными пользователями/устройствами, выполнить actions и сравнить состояние: active player, pot, cards visibility, timers, available actions, player statuses. Дополнительно проверить серверное состояние через API/БД/логи.

### Вопросы по sync

**Что такое synchronization между клиентами?**

Synchronization - это согласование состояния между клиентами и сервером, чтобы все участники видели актуальную и одинаковую картину. В poker это особенно важно для table state, actions, timers и pot.

**Как проверить синхронизацию состояния между двумя или несколькими клиентами?**

Запустить несколько клиентов, выполнить действие на одном и проверить, что остальные получили правильное обновление без задержек, дубликатов и старых данных. Также полезно проверять server state через API или logs.

**Что делать, если один клиент получил событие, а другой нет?**

Нужно проверить WebSocket connection, subscriptions, user/table room, server logs, client logs и механизм восстановления состояния. Хорошая система должна после reconnect или refresh получить актуальный snapshot с сервера.

**Как проверить порядок событий?**

Создать сценарий с несколькими быстрыми actions и проверить, что события применяются в правильной последовательности. Можно смотреть timestamps, event ids, sequence numbers и логи на клиенте/сервере.

**Что такое duplicate event?**

Duplicate event - это одно и то же событие, полученное или обработанное больше одного раза. Например, клиент дважды получил событие `player_raised` и дважды увеличил pot в UI.

**Что такое missed event?**

Missed event - событие, которое должно было прийти клиенту, но не пришло. Например, один игрок сделал fold, сервер событие отправил, но другой клиент его не получил.

**Что такое out-of-order event?**

Out-of-order event - событие, пришедшее не в том порядке. Например, клиент сначала получил `hand_finished`, а потом `player_raised` для этой hand. Система должна уметь игнорировать или корректно обрабатывать такие случаи.

**Как проверить, что после действия одного игрока остальные видят обновление?**

Выполнить action на одном клиенте и проверить на других клиентах UI, available actions, pot, active player, timer и историю событий. Для надежности сверить это с server response и логами.

**Как проверить, что UI не показывает старое состояние?**

Проверить refresh, reconnect, смену вкладок, background/foreground, медленную сеть и повторный вход за стол. Клиент должен брать актуальное состояние с сервера, а не слепо доверять локальному cache/state.

**Как проверить таймеры у разных игроков?**

Открыть один стол на нескольких клиентах и сравнить timer behavior: старт, окончание, смена active player, действия при timeout. Допустима небольшая визуальная разница, но бизнес-событие должно срабатывать одинаково для всех.

### Вопросы по reconnect

**Что такое reconnect?**

Reconnect - восстановление соединения клиента с сервером после потери сети, закрытия соединения, background/foreground или другой временной проблемы. После reconnect клиент должен получить актуальное состояние.

**Какие сценарии reconnect нужно проверять?**

Потеря сети, переключение Wi-Fi/mobile data, background/foreground, lock/unlock устройства, server restart, WebSocket disconnect, timeout, reconnect во время hand, во время action и после окончания timer.

**Что должно произойти, если пользователь потерял сеть во время hand?**

Сервер должен продолжить быть source of truth. Клиент должен показать потерю соединения или reconnecting state, а после восстановления получить актуальный table snapshot: hand state, pot, active player, timer и статус самого игрока.

**Что должно произойти, если пользователь вернулся через 5 секунд, 30 секунд, 2 минуты?**

Через 5 секунд пользователь может вернуться в текущую hand, если она еще идет. Через 30 секунд состояние может уже измениться, поэтому нужен актуальный snapshot. Через 2 минуты hand может закончиться или игрок может быть removed/sitting out, зависит от правил продукта.

**Как клиент должен восстановить актуальное состояние после reconnect?**

Клиент должен переподключиться, заново авторизоваться при необходимости, подписаться на нужный table/channel и запросить текущий server snapshot. Нельзя полагаться только на локальное состояние до disconnect.

**Нужно ли переотправлять action после reconnect?**

Не всегда. Если action был отправлен, но response потерялся, нужно проверить статус action на сервере. Повторная отправка без idempotency может привести к duplicate action, поэтому лучше использовать action id/request id/idempotency key.

**Как избежать двойной отправки action?**

Блокировать кнопку после отправки, использовать unique request/action id, idempotency key на сервере и проверять текущее game state. Сервер должен не применять одно и то же действие дважды.

**Что делать, если request ушел, но response не дошел до клиента?**

Клиент должен запросить актуальное состояние или статус операции, а не автоматически повторять опасный request. Для критичных операций нужен idempotency key, чтобы повторный request не создал дубликат.

**Как проверить reconnect на mobile при background/foreground?**

Зайти за стол, отправить приложение в background, подождать разное время, вернуть в foreground и проверить reconnect, актуальный table state, таймеры, actions, отсутствие crash и корректность UI.

**Как проверить reconnect при смене Wi-Fi на mobile data?**

Во время активной сессии переключить сеть, дождаться disconnect/reconnect и проверить, что клиент восстановил соединение, не потерял авторизацию и получил актуальное состояние без дубликатов событий.

### Вопросы по error handling

**Какие бывают типы ошибок в client-server взаимодействии?**

Ошибки бывают network errors, timeout, validation errors, auth errors, permission errors, business logic conflicts, server errors, parsing/schema errors и real-time connection errors.

**Как клиент должен обрабатывать `400`, `401`, `403`, `404`, `409`, `422`, `500`, timeout?**

`400/422` - показать ошибку валидации или бизнес-правила. `401` - перелогин или refresh token. `403` - нет прав. `404` - ресурс не найден. `409` - конфликт состояния, нужно обновить данные. `500` - server error, показать понятное сообщение. Timeout - retry или reconnect, если это безопасно.

**Чем отличается client error от server error?**

Client error - проблема в request или правах пользователя, обычно `4xx`. Server error - проблема на стороне сервера или инфраструктуры, обычно `5xx`. QA проверяет, что ошибка классифицирована правильно.

**Что должен видеть пользователь при ошибке?**

Понятное сообщение без технических деталей, возможность повторить действие или вернуться в стабильное состояние. Нельзя показывать stack trace, SQL errors или внутренние server messages.

**Что должно логироваться при ошибке?**

Request id/correlation id, user id, endpoint/event, payload без sensitive data, status code, error code, timestamp, device/app version, session id, table id/hand id и stack trace на сервере.

**Как проверить retry logic?**

Сымитировать timeout, temporary `500/503`, network drop и проверить, сколько раз клиент повторяет request, с каким интервалом, не создает ли дубликаты и останавливается ли после лимита.

**Когда retry безопасен, а когда опасен?**

Retry обычно безопасен для GET и идемпотентных операций. Опасен для POST/action/payment/bet, если нет idempotency, потому что можно создать дубликат действия или транзакции.

**Что такое idempotency и зачем она нужна при retry?**

Idempotency означает, что повторный одинаковый request приводит к тому же результату, а не создает новое действие. Она нужна, чтобы retry не вызвал двойное списание баланса, двойной raise или duplicate transaction.

**Как проверить, что ошибка не ломает состояние игры?**

После ошибки проверить server state, UI state, БД, логи и состояние других клиентов. Например, если action отклонен, pot, balance и active player не должны измениться некорректно.

**Как проверить, что после ошибки можно продолжить нормальную работу?**

Вызвать ошибку, затем выполнить валидное действие или refresh/reconnect и убедиться, что пользователь может продолжить игру, UI не завис, кнопки активны корректно, состояние актуально.

### Вопросы по poker platform

**Как протестировать, что действие `raise` применилось только один раз?**

Отправить `raise`, затем повторить request или быстро нажать кнопку несколько раз. Проверить pot, balance, action history, server logs и events на других клиентах. Должно быть одно действие и одно изменение баланса.

**Как проверить, что баланс не списался дважды при повторном request?**

Сравнить баланс до и после, проверить `transactions`, action history и logs. Повторный request с тем же idempotency key должен вернуть тот же результат или быть отклонен без второго списания.

**Как проверить, что игрок не может сделать action после истечения таймера?**

Дождаться timeout и отправить action сразу после истечения времени, включая request через API. Сервер должен отклонить action, а UI должен показать актуальное состояние и следующего active player.

**Как проверить, что disconnected player корректно возвращается за стол?**

Отключить сеть во время hand, включить обратно и проверить reconnect, актуальный snapshot, статус игрока, доступные actions, баланс, таймер и события, которые произошли во время disconnect.

**Что должно быть источником истины: клиент или сервер?**

Сервер. Клиент может отображать предварительное состояние, но финальные правила игры, баланс, валидность action и результат hand должны определяться сервером.

**Как проверить, что разные игроки видят один и тот же pot, cards state, active player и timer?**

Открыть стол несколькими пользователями, выполнить серию actions и сравнить UI на всех клиентах. Дополнительно проверить server snapshot/API/логи, чтобы понять, где расхождение: клиент, сеть или сервер.

**Что проверить, если один игрок сделал fold, а другой клиент этого не увидел?**

Проверить, ушел ли action на сервер, записался ли в logs/DB, отправил ли сервер event второму клиенту, был ли второй клиент подписан на нужный channel, не было ли disconnect/missed event и восстановился ли state после refresh/reconnect.

**Как проверить поведение при медленной сети?**

Использовать throttling, network conditioner или реальные плохие условия. Проверить latency, reconnecting state, timeouts, duplicate clicks, disabled buttons, retry logic и актуальность состояния после восстановления.

**Как проверить поведение при потере WebSocket-соединения?**

Принудительно разорвать WebSocket или сеть, проверить UI состояние, попытки reconnect, повторную подписку на table events, получение snapshot и отсутствие missed/duplicate events после восстановления.

**Какие логи нужны для анализа бага в real-time игре?**

Нужны client logs, server logs, WebSocket events, request/response, correlation id, user id, table id, hand id, timestamps, app version, device/network info, backend service logs и изменения в БД/transactions.

### Хороший ответ на интервью

"При тестировании client-server взаимодействия я проверяю не только отдельный request/response, но и полный flow: что клиент отправил, как сервер обработал данные, что изменилось в БД, какие события получили другие клиенты и как UI обновился. Для real-time продукта особенно важны sync, reconnect, duplicate requests, missed events, out-of-order events, latency и error handling. В poker platform сервер должен быть источником истины, потому что клиенту нельзя доверять игровую логику, баланс и результат hand."

## Commands / Terms

| Term | Meaning |
| --- | --- |
| Client-server architecture | Модель, где клиент отправляет запросы, а сервер обрабатывает бизнес-логику и данные. |
| Source of truth | Основной источник корректного состояния системы; для игровой логики это сервер. |
| WebSocket | Постоянное соединение для real-time событий между клиентом и сервером. |
| Polling | Регулярные запросы клиента к серверу в поиске обновлений. |
| Latency | Задержка между действием и реакцией системы. |
| Race condition | Ошибка, когда результат зависит от порядка параллельных событий. |
| Stale data | Устаревшие данные на клиенте или в cache. |
| Idempotency key | Уникальный ключ request, который помогает не применить опасную операцию дважды. |
| Correlation id | Идентификатор для связывания request, events и logs при расследовании бага. |
