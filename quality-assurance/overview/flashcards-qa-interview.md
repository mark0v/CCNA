## 🔵 ТЕОРИЯ ТЕСТИРОВАНИЯ

**Q: Чем отличается QA от QC от Tester?**
A: **QA** (Quality Assurance) — процессный подход, предотвращение дефектов. **QC** (Quality Control) — проверка продукта на соответствие требованиям. **Tester** — выполняет тестирование, находит дефекты.

---

**Q: Назови 7 принципов тестирования**
A: 1. Тестирование показывает наличие дефектов, но не их отсутствие. 2. Исчерпывающее тестирование невозможно. 3. Раннее тестирование экономит время и деньги. 4. Скопление дефектов (дефекты кластеризуются). 5. Парадокс пестицида (повторные тесты теряют эффективность). 6. Тестирование зависит от контекста. 7. Заблуждение об отсутствии ошибок.

---

**Q: Разница Error, Defect, Failure?**
A: **Error** — ошибка человека (разработчика/аналитика). **Defect** — результат ошибки в коде/документе (баг). **Failure** — проявление дефекта при выполнении (видимый сбой).

---

**Q: Verification vs Validation?**
A: **Verification** — "Правильно ли мы создаём продукт?" (проверка соответствия спецификации). **Validation** — "Правильный ли продукт мы создаём?" (проверка соответствия нуждам пользователя). Verification — статическая, Validation — динамическая.

---

**Q: Чем отличается Priority от Severity?**
A: **Severity** — степень влияния дефекта на функциональность (техническая характеристика). **Priority** — срочность исправления (бизнес-характеристика). Пример HIGH Severity / LOW Priority: опечатка в ошибке при краше. Пример LOW Severity / HIGH Priority: опечатка в логотипе на главной странице.

---

**Q: Какие фазы STLC?**
A: 1. Requirements Analysis, 2. Test Planning, 3. Test Case Design, 4. Test Environment Setup, 5. Test Execution, 6. Test Cycle Closure.

---

**Q: Smoke vs Sanity testing?**
A: **Smoke** — поверхностная проверка всей системы ("не горит ли?"). Запускается при каждом билде. **Sanity** — глубокая проверка конкретного функционала после фикса. Subset регрессии.

---

**Q: Чем отличается Re-testing от Regression testing?**
A: **Re-testing** — повторное выполнение теста, который ранее провалился, для проверки конкретного фикса. **Regression** — тестирование всего приложения, чтобы убедиться что фикс ничего не сломал в других местах.

---

**Q: Static vs Dynamic testing?**
A: **Static** — проверка без запуска кода: reviews, walkthroughs, inspections, code analysis. **Dynamic** — проверка при работающей программе: функциональное, нагрузочное тестирование.

---

**Q: Какие уровни тестирования ты знаешь?**
A: **Unit** (модульное — изолированный компонент), **Integration** (взаимодействие между компонентами), **System** (вся система целиком), **Acceptance/UAT** (соответствие бизнес-требованиям, финальная проверка перед релизом).

---

**Q: Что такое Equivalence Partitioning?**
A: Техника тест-дизайна: разбиваем входные данные на классы эквивалентности, где все значения класса обрабатываются одинаково. Тестируем по одному значению из каждого класса (valid + invalid классы).

---

**Q: Что такое Boundary Value Analysis?**
A: Техника тест-дизайна: тестируем граничные значения диапазона. Для диапазона 1-100 тестируем: 0 (ниже min), 1 (min), 2 (min+1), 99 (max-1), 100 (max), 101 (выше max).

---

**Q: Что такое Decision Table Testing?**
A: Техника тест-дизайна для систем с несколькими условиями. Таблица: столбцы = тест-кейсы, строки = условия и результаты. Помогает покрыть все комбинации условий и не пропустить кейсы.

---

**Q: Что такое Pairwise Testing?**
A: Техника для уменьшения числа тест-кейсов при многих параметрах. Каждая пара значений параметров тестируется хотя бы один раз. Инструмент: PICT (Microsoft).

---

**Q: Что такое Risk-Based Testing?**
A: Подход к тестированию, при котором приоритет тест-кейсов определяется на основе рисков: вероятность дефекта × влияние на бизнес. Высокорисковые области тестируются более тщательно.

---

**Q: Что такое Traceability Matrix (RTM)?**
A: Requirements Traceability Matrix — документ, связывающий каждое требование с соответствующими тест-кейсами. Обеспечивает полноту покрытия требований тестами.

---

**Q: Какие основные метрики QA ты знаешь?**
A: **Defect Density** (дефекты/размер модуля), **Pass Rate** (% прошедших тестов), **Defect Removal Efficiency** (% дефектов найденных до релиза), **Test Coverage** (% требований покрытых тестами), **Mean Time to Detect** (среднее время обнаружения дефекта), **Escape Rate** (дефекты ускользнувшие в продакшн).

## 🌐 WEB ТЕСТИРОВАНИЕ

**Q: Какие HTTP методы ты знаешь? В чём разница PUT и PATCH?**
A: **GET** (получить), **POST** (создать), **PUT** (полностью заменить), **PATCH** (частично обновить), **DELETE** (удалить). PUT — заменяет объект целиком (непереданные поля обнуляются). PATCH — обновляет только переданные поля.

---

**Q: Что означают HTTP статус-коды 2xx, 3xx, 4xx, 5xx?**
A: **2xx** — успех (200 OK, 201 Created, 204 No Content). **3xx** — перенаправление (301 Moved Permanently, 302 Found). **4xx** — ошибка клиента (400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found, 422 Unprocessable). **5xx** — ошибка сервера (500 Internal Error, 502 Bad Gateway, 503 Unavailable).

---

**Q: Что такое 3-Tier Architecture?**
A: **Presentation Tier** (UI — браузер/мобильное приложение), **Application Tier** (Backend — бизнес-логика, API), **Data Tier** (Database — хранение данных). QA тестирует каждый уровень: UI тесты, API тесты, DB тесты.

---

**Q: Чем отличается SOAP от REST?**
A: **REST** — архитектурный стиль, использует HTTP методы, JSON/XML, stateless, гибкий. **SOAP** — протокол, XML, строгая схема (WSDL), stateful возможен, более сложный. REST проще и быстрее, SOAP надёжнее для транзакций (банки, legacy).

---

**Q: Что такое CORS и зачем он нужен?**
A: Cross-Origin Resource Sharing — механизм браузера, позволяющий/запрещающий запросы к ресурсам другого домена. Тестировщик проверяет: нужные домены разрешены, лишние — заблокированы.

---

**Q: Что можно найти во вкладке Network в Chrome DevTools?**
A: Все HTTP/HTTPS запросы страницы, их URL, методы, статус-коды, заголовки запроса и ответа, тело запроса и ответа (payload), время выполнения, размер. Полезно для дебага API взаимодействий.

---

**Q: Что такое виды аутентификации?**
A: **Basic Auth** (Base64 логин:пароль), **Session/Cookie** (сессионный токен), **JWT Bearer Token** (Header.Payload.Signature), **OAuth 2.0** (авторизация через третий сервис), **API Key** (статический ключ), **SSO** (единый вход).

---

## 🔌 API ТЕСТИРОВАНИЕ

**Q: Что проверяешь при тестировании API endpoint?**
A: 1. Статус-код (200/201/400/404/500). 2. Тело ответа (правильная структура, поля, значения). 3. Заголовки (Content-Type, Cache-Control). 4. Время ответа. 5. Негативные кейсы (пустые поля, неверный тип, без авторизации). 6. Граничные значения. 7. Данные в БД после запроса.

---

**Q: Что такое idempotent HTTP метод?**
A: Метод, многократное выполнение которого даёт тот же результат, что и однократное. GET, PUT, DELETE — идемпотентны. POST, PATCH — нет (POST создаёт новую запись каждый раз).

---

**Q: Что такое JSON? Какие типы данных есть в JSON?**
A: JSON (JavaScript Object Notation) — формат обмена данными. Типы: **string** ("text"), **number** (42, 3.14), **boolean** (true/false), **null**, **array** ([1,2,3]), **object** ({"key": "value"}). Вложенные структуры поддерживаются.

---

**Q: Как написать assertion в Postman для проверки статус-кода?**
A: `pm.test("Status is 200", () => { pm.response.to.have.status(200); });`  
Для проверки поля: `pm.test("Name correct", () => { const json = pm.response.json(); pm.expect(json.name).to.eql("expected"); });`

## 📱 MOBILE ТЕСТИРОВАНИЕ

**Q: Разница между Native, Hybrid и Mobile Web приложениями?**
A: **Native** — написано на нативном языке (Swift/ObjC для iOS, Kotlin/Java для Android). Лучший UX, полный доступ к API. **Hybrid** — веб внутри нативной оболочки (React Native, Ionic). Одна кодовая база. **Mobile Web** — адаптивный сайт в мобильном браузере, не устанавливается.

---

**Q: В чём разница Emulator и Simulator?**
A: **Simulator** (iOS) — симулирует поведение, не эмулирует железо, только macOS, быстрее, ограниченные аппаратные функции. **Emulator** (Android) — эмулирует реальное железо, медленнее, больше аппаратных возможностей.

---

**Q: Что такое Interrupt Testing для мобильных?**
A: Тестирование поведения приложения при прерываниях: входящий звонок, SMS, push-нотификация, низкий заряд батареи, потеря сети — во время активного использования приложения.

---

**Q: Как читать Android логи через ADB?**
A: `adb logcat` — все логи. `adb logcat -s "MyTag"` — фильтр по тегу. `adb logcat *:E` — только ошибки. Крэш искать по `FATAL EXCEPTION` и `AndroidRuntime`. Уровни: V(erbose), D(ebug), I(nfo), W(arning), E(rror).

---

## 🗄️ БАЗЫ ДАННЫХ

**Q: В чём разница INNER JOIN, LEFT JOIN, RIGHT JOIN?**
A: **INNER JOIN** — только строки с совпадением в обеих таблицах. **LEFT JOIN** — все строки из левой + совпадения из правой (NULL где нет совпадения). **RIGHT JOIN** — все строки из правой + совпадения из левой. **FULL OUTER JOIN** — все строки из обеих таблиц.

---

**Q: Как найти дубликаты в таблице SQL запросом?**
A: `SELECT email, COUNT(*) as cnt FROM users GROUP BY email HAVING COUNT(*) > 1;`

---

**Q: Чем SQL отличается от NoSQL?**
A: **SQL** — реляционные БД, строгая схема, таблицы, JOIN, ACID транзакции (PostgreSQL, MySQL). **NoSQL** — гибкая схема, горизонтальное масштабирование, разные модели (документы, key-value, граф). MongoDB (документы), Redis (key-value).

## ⚡ PERFORMANCE ТЕСТИРОВАНИЕ

**Q: Чем отличается Load от Stress тестирования?**
A: **Load Testing** — проверка при ожидаемой/нормальной нагрузке (например 1000 concurrent users). **Stress Testing** — нагрузка ВЫШЕ нормальной, ищем точку отказа системы. Stress также проверяет восстановление (graceful degradation).

---

**Q: Что такое Stability (Soak) Testing?**
A: Тестирование при нормальной нагрузке на длительное время (8-24 часа). Цель: обнаружить Memory Leaks (утечки памяти) и деградацию производительности со временем.

---

**Q: Какие ключевые метрики производительности?**
A: **Response Time** (время ответа, цель <2с), **Throughput/RPS** (запросов в секунду), **Error Rate** (% ошибок, цель <1%), **CPU Usage** (<80% под нагрузкой), **Memory Usage** (нет роста со временем), **Latency** (задержка, цель <200ms).

---

## ⚙️ CI/CD И ИНСТРУМЕНТЫ

**Q: Что такое CI/CD?**
A: **CI** (Continuous Integration) — автоматическая сборка и тестирование при каждом коммите. **CD** (Continuous Delivery) — автодоставка на staging. **CD** (Continuous Deployment) — автодеплой на продакшн. QA: автотесты запускаются в pipeline, smoke тесты после деплоя.

---

**Q: Основные команды Git для QA?**
A: `git clone` (клонировать), `git status` (статус), `git add .` (подготовить к коммиту), `git commit -m "msg"` (сохранить), `git push` (отправить), `git pull` (получить), `git checkout -b branch` (создать ветку).

---

**Q: Зачем QA нужен Docker?**
A: Запуск изолированного тестового окружения одной командой (`docker-compose up`). Просмотр логов приложения (`docker logs`). Воспроизведение production-like среды локально. Одинаковое окружение у всей команды.
