## Кратко

Производительность сайта зависит от всей цепочки доставки и обработки данных:

```text
DNS/TLS -> CDN/сервер -> HTML -> CSS/JS/шрифты/изображения
-> основной поток браузера -> отрисовка -> взаимодействие пользователя
```

QA-инженеру следует сочетать:

- **лабораторные тесты** — контролируемые синтетические измерения;
- **полевые данные и RUM** — опыт реальных пользователей, устройств и сетей;
- **нагрузочное тестирование** — поведение backend при конкурентном трафике;
- **функциональные проверки** — корректность работы в медленной или нестабильной среде.

Одна оценка Lighthouse или одно значение времени загрузки не описывают пользовательский опыт полностью.

## Главное

- Актуальные Core Web Vitals: `LCP`, `INP` и `CLS`.
- Рекомендуемые полевые пороги: LCP <= 2,5 с, INP <= 200 мс, CLS <= 0,1 на 75-м перцентиле.
- Lighthouse не измеряет реальный полевой INP; лабораторным приближением служит Total Blocking Time.
- Лабораторные и полевые данные отвечают на разные вопросы.
- TTFB помогает оценить вклад сервера и сети, но не описывает скорость всей страницы.
- Частые узкие места: тяжёлый JavaScript, блокирующие ресурсы, изображения, шрифты и сторонние скрипты.
- Проверять нужно холодный и прогретый кеш, мобильные и настольные устройства, разные сети и регионы.
- Performance budget должен включать пользовательские метрики, размеры ресурсов и количество запросов.
- Тестирование страницы и нагрузочное тестирование сервера дополняют друг друга.

## Лабораторные и полевые данные

| Данные | Преимущество | Ограничение |
| --- | --- | --- |
| Лабораторные | Повторяемы, удобны для диагностики, доступны до релиза | Устройство, сеть и действия пользователя моделируются |
| Полевые / RUM | Показывают реальные устройства, сети и поведение | Более шумные, поступают с задержкой, требуют достаточного трафика |

Лабораторные данные помогают находить причины проблем и предотвращать регрессии. Полевые данные показывают фактический пользовательский опыт.

PageSpeed Insights может отображать два набора данных:

- полевые данные Chrome User Experience Report, если они доступны;
- лабораторный аудит Lighthouse.

Их нельзя сравнивать как результаты одного и того же измерения.

## Core Web Vitals

| Метрика | Что показывает | Хорошее значение |
| --- | --- | ---: |
| LCP | Скорость загрузки крупнейшего видимого элемента | <= 2,5 с |
| INP | Отзывчивость страницы при взаимодействиях | <= 200 мс |
| CLS | Визуальную стабильность страницы | <= 0,1 |

Для полевых данных оценивают 75-й перцентиль отдельно для мобильного и настольного трафика.

В 2024 году INP заменил FID в составе Core Web Vitals.

## Дополнительные метрики

- **TTFB:** время до первого байта ответа;
- **FCP:** время до первого отрисованного текста, изображения или другого содержимого;
- **TBT:** лабораторная оценка блокировки основного потока;
- **Speed Index:** скорость визуального заполнения страницы;
- **DOMContentLoaded / load:** события жизненного цикла документа;
- **размер и количество ресурсов:** стоимость передачи и обработки запросов.

Дополнительную метрику нельзя превращать в универсальный критерий прохождения без учёта продукта и сценария.

## Частые узкие места

### Сервер и сеть

- медленный origin-сервер;
- удалённый регион;
- отсутствие CDN или кеширования;
- задержки DNS и TLS;
- перегруженный backend;
- медленная база данных или API;
- лишние перенаправления;
- слишком большой HTML;
- неэффективное сжатие.

### CSS и JavaScript

- CSS, блокирующий отрисовку;
- большие JavaScript-бандлы;
- неиспользуемый код;
- долгие задачи в основном потоке;
- дорогая гидратация;
- синхронные сторонние скрипты;
- частые перерасчёты стилей и компоновки.

Перенос всех скриптов в конец страницы не является универсальным решением. `defer`, `async`, разделение кода и стратегию загрузки выбирают с учётом зависимостей.

### Изображения, шрифты и медиа

- изображения избыточного размера;
- неэффективный формат;
- отсутствие адаптивных изображений;
- ранняя загрузка содержимого ниже первого экрана;
- отсутствие размеров изображения, вызывающее CLS;
- медленная загрузка шрифтов;
- автоматическое воспроизведение или тяжёлые медиафайлы.

### Сторонние компоненты

- аналитика;
- менеджеры тегов;
- реклама;
- чат-виджеты;
- социальные вставки;
- платформы управления согласием.

Для каждого стороннего компонента оценивают сетевой трафик, нагрузку на основной поток и влияние на приватность.

### Хостинг и доступные ресурсы

Общий или нестабильный хостинг, нехватка CPU, медленный диск и исчерпанные пулы соединений могут увеличивать TTFB. Проверять систему нужно под реалистичным трафиком, а не только одним запросом.

## Матрица проверок

Следует покрыть:

- мобильные и настольные устройства;
- слабые и производительные устройства;
- быструю и ограниченную сеть;
- холодный и прогретый кеш;
- первый и повторный просмотр;
- анонимного и авторизованного пользователя;
- основные страницы и шаблоны;
- разные географические точки;
- пустые и заполненные данными состояния;
- сравнение со включёнными и отключёнными сторонними компонентами.

## Инструменты

### Chrome DevTools

- водопад запросов Network;
- трассировка Performance;
- ограничение CPU и сети;
- анализ покрытия кода;
- диагностика отрисовки;
- локальная подмена ресурсов.

### Lighthouse

Подходит для повторяемого лабораторного аудита и диагностики. Итоговая оценка зависит от окружения и версии Lighthouse, поэтому дополнительно отслеживают отдельные метрики и бюджеты.

### PageSpeed Insights

Объединяет лабораторные данные Lighthouse и полевые данные CrUX, если они доступны.

### WebPageTest

Позволяет выбирать:

- расположение и браузер;
- первый и повторный просмотр;
- покадровую ленту и видео;
- водопад запросов;
- представление соединений;
- сценарии действий.

### RUM и APM

Производственная телеметрия помогает анализировать:

- Web Vitals по страницам;
- сегменты устройств, сетей и регионов;
- различия между релизами;
- ошибки JavaScript;
- время API-запросов;
- долгие задачи.

## Performance budget

Пример:

```text
LCP p75 mobile <= 2.5 s
INP p75 mobile <= 200 ms
CLS p75 <= 0.1
Lighthouse lab LCP <= 2.5 s
initial JS transfer <= 250 KB compressed
third-party JS <= 100 KB compressed
critical page requests <= 60
```

Бюджеты должны учитывать особенности продукта и храниться с версией. Ограничения на ресурсы помогают заметить регрессию до ухудшения полевых метрик.

## Процесс тестирования

1. Выбрать критичные страницы и пользовательские сценарии.
2. Зафиксировать исходные полевые показатели.
3. Определить бюджеты и критерии прохождения.
4. Зафиксировать лабораторное окружение и версии инструментов.
5. Выполнить несколько измерений, а не одно.
6. Проанализировать водопад запросов и основной поток.
7. Сопоставить frontend-метрики с данными backend и APM.
8. Повторить тесты с холодным и прогретым кешем на мобильном и настольном профилях.
9. Сравнить результаты до и после изменения.
10. После релиза контролировать полевые показатели.

## Поведение в медленных и нестабильных условиях

Проверить, что:

- отображается индикатор загрузки;
- элементы управления не допускают повторную отправку;
- при тайм-ауте показаны понятная ошибка и повтор действия;
- частично загруженное содержимое остаётся доступным;
- изображения имеют стабильные заполнители;
- навигация не теряет состояние;
- ошибки сети и ресурсов обрабатываются контролируемо;
- устаревшие данные помечены, если этого требует продукт.

Хорошие метрики не компенсируют сломанное поведение.

## Связь с нагрузочным тестированием

Синтетический тест страницы отвечает на вопрос:

```text
Насколько быстро один браузер загружает и обрабатывает страницу?
```

Нагрузочный тест backend отвечает на другой вопрос:

```text
Как сервис работает при множестве одновременных запросов?
```

Нужны оба вида тестирования. Быстрая страница на свободном backend может замедлиться под трафиком, а быстрый API не гарантирует быструю отрисовку.

## Типичные дефекты

- LCP-изображение обнаруживается слишком поздно;
- JavaScript блокирует взаимодействие;
- баннер cookie вызывает смещение макета;
- сторонний скрипт блокирует основной поток;
- повторный просмотр быстрый, а первый — медленный;
- мобильные полевые данные не проходят критерий, хотя настольный лабораторный тест успешен;
- кеш скрывает медленный origin-сервер;
- мобильное устройство загружает изображение для настольного разрешения;
- API работает быстро, но клиентская отрисовка занимает много времени;
- оценка Lighthouse улучшается, а реальный INP ухудшается.

## Отчёт

Указать:

- URL и версию сборки;
- устройство, браузер и регион;
- профиль сети и CPU;
- состояние кеша;
- количество запусков;
- медиану и разброс результатов;
- LCP, INP, CLS или лабораторные приближения;
- TTFB, FCP, TBT и Speed Index;
- размер переданных данных и количество запросов;
- водопад запросов или трассировку;
- сегменты полевых данных;
- сопоставление с backend;
- результат проверки бюджета и рекомендацию.

## Чек-лист QA

- [ ] Выбраны критичные страницы и сценарии.
- [ ] Лабораторные и полевые данные разделены.
- [ ] Используются актуальные Core Web Vitals.
- [ ] Мобильные и настольные данные измеряются отдельно.
- [ ] Проверены холодный и прогретый кеш.
- [ ] Сравнены результаты нескольких запусков.
- [ ] Проанализированы водопад запросов и основной поток.
- [ ] Результаты сопоставлены с backend или APM.
- [ ] Измерено влияние сторонних компонентов.
- [ ] Бюджеты версионируются.
- [ ] Проверено функциональное поведение при задержках и ошибках.
- [ ] После релиза отслеживаются полевые метрики.
