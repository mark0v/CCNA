## 🔵 ЧАСТЬ 1: Теория тестирования (вопросы 1–15)

**1. Какой из вариантов ПРАВИЛЬНО описывает разницу Error и Defect?**

a) Error и Defect — синонимы  
b) Error — ошибка человека, Defect — следствие ошибки в коде/документе ✅  
c) Defect — ошибка человека, Error — следствие  
d) Error — это только runtime ошибки  

> **Ответ: B.** Error совершает человек (неправильное понимание требований), Defect — это результат этой ошибки в артефакте (коде, тест-кейсе, документе).

---

**2. Bug с HIGH Severity и LOW Priority — это:**

a) Такой комбинации не существует  
b) Крэш приложения при входе администратора, которым пользуются 2 раза в год ✅  
c) Опечатка в названии кнопки на главной странице  
d) Неправильный цвет кнопки в footer  

> **Ответ: B.** HIGH Severity — сильно влияет на функциональность (крэш). LOW Priority — редко используется, не срочно исправлять.

---

**3. Какой принцип тестирования гласит: "Повторяющиеся тесты со временем теряют эффективность"?**

a) Принцип раннего тестирования  
b) Принцип кластеризации дефектов  
c) Принцип парадокса пестицида ✅  
d) Принцип исчерпывающего тестирования  

> **Ответ: C.** Парадокс пестицида — как насекомые вырабатывают иммунитет к пестициду, так и тесты со временем перестают находить новые дефекты. Решение: регулярно обновлять тест-кейсы.

---

**4. В STLC (Software Testing Life Cycle) первая фаза — это:**

a) Test Case Design  
b) Test Planning  
c) Requirements Analysis ✅  
d) Test Execution  

> **Ответ: C.** STLC начинается с Requirements Analysis — изучение требований и определение тестируемости. Затем: Planning → Design → Environment Setup → Execution → Closure.

---

**5. Какая техника тест-дизайна ЛУЧШЕ подходит для формы логина с полями email + пароль?**

a) Boundary Value Analysis  
b) State Transition Testing  
c) Equivalence Partitioning ✅  
d) Use Case Testing  

> **Ответ: C.** Equivalence Partitioning — делим данные на классы: valid email / invalid email / пустой; valid пароль / short пароль / пустой. Тестируем по одному значению из каждого класса.

---

**6. Что такое Sanity Testing?**

a) Полная проверка всей системы при каждом новом билде  
b) Проверка конкретного функционала после фикса, subset регрессии ✅  
c) Тестирование удобства использования  
d) Тестирование при нестандартных условиях  

> **Ответ: B.** Sanity Testing — быстрая целевая проверка конкретного функционала, чтобы убедиться что фикс работает. Отличается от Smoke (весь продукт) и Regression (все тесты).

---

**7. Чем Verification отличается от Validation?**

a) Это одно и то же, просто разные названия  
b) Verification — динамическая, Validation — статическая  
c) Verification — "правильно ли мы строим?", Validation — "правильный ли продукт мы строим?" ✅  
d) Verification — только для кода, Validation — только для UI  

> **Ответ: C.** Verification — соответствие спецификации (статические проверки, reviews). Validation — соответствие реальным нуждам пользователя (UAT, beta-тестирование).

---

**8. Test Strategy и Test Plan — в чём ключевая разница?**

a) Это одно и то же  
b) Test Strategy — высокоуровневый документ (КАК тестировать проект в целом), Test Plan — детальный (ЧТО тестировать в конкретном цикле) ✅  
c) Test Plan — высокоуровневый, Test Strategy — детальный  
d) Test Strategy создаётся после Test Plan  

> **Ответ: B.** Test Strategy — общий подход (уровни, техники, инструменты, окружения). Создаётся один раз для проекта. Test Plan — детали конкретного тест-цикла (scope, timeline, resources).

---

**9. Что такое Pairwise Testing?**

a) Тестирование с напарником  
b) Тестирование всех возможных комбинаций параметров  
c) Техника, при которой каждая пара значений параметров тестируется хотя бы один раз ✅  
d) Тестирование двух версий приложения одновременно  

> **Ответ: C.** Pairwise (попарное) тестирование — сокращает число тест-кейсов, охватывая все пары комбинаций. Если 3 параметра по 3 значения — вместо 27 кейсов достаточно ~9.

---

**10. Какой уровень тестирования проверяет взаимодействие между компонентами?**

a) Unit Testing  
b) Integration Testing ✅  
c) System Testing  
d) Acceptance Testing  

> **Ответ: B.** Integration Testing — проверка взаимодействия между модулями/сервисами. Стратегии: Big Bang, Top-Down, Bottom-Up, Sandwich.

---

**11. RTM (Requirements Traceability Matrix) нужна для:**

a) Отслеживания времени тестирования  
b) Связи каждого требования с тест-кейсами для обеспечения полноты покрытия ✅  
c) Записи результатов тестирования  
d) Отслеживания статуса багов  

> **Ответ: B.** RTM показывает: какое требование → какие тест-кейсы его проверяют. Помогает убедиться что все требования покрыты тестами и ни одно не пропущено.

---

**12. Какая метрика QA показывает % дефектов, найденных ДО релиза?**

a) Pass Rate  
b) Defect Density  
c) Test Coverage  
d) Defect Removal Efficiency (DRE) ✅  

> **Ответ: D.** DRE = (дефекты найденные до релиза / все дефекты) × 100%. Высокий DRE (>90%) означает эффективное тестирование.

---

**13. Exploratory Testing — это:**

a) Автоматизированное исследование кода  
b) Тестирование без тест-кейсов, одновременное планирование и выполнение ✅  
c) Тестирование на основе требований  
d) Стресс-тестирование  

> **Ответ: B.** Exploratory Testing — тестировщик исследует приложение без заранее написанных тест-кейсов, опираясь на опыт и интуицию. Хорошо находит неожиданные баги.

---

**14. State Transition Testing применяется когда:**

a) Нужно протестировать граничные значения  
b) Система имеет разные состояния и переходы между ними ✅  
c) Нужно уменьшить число комбинаций  
d) Требования описаны в виде таблицы  

> **Ответ: B.** State Transition Testing — для систем с состояниями (например: NEW → IN_PROGRESS → DONE → CLOSED). Тестируем: правильные переходы, неправильные переходы, все состояния.

---

**15. Что такое Test Impact Analysis?**

a) Анализ влияния тестирования на производительность  
b) Определение какие тест-кейсы нужно запустить после конкретных изменений в коде ✅  
c) Оценка бюджета на тестирование  
d) Анализ метрик тестирования  

> **Ответ: B.** Test Impact Analysis помогает определить минимальный необходимый набор тестов после изменений, экономя время без потери качества.

## 🌐 ЧАСТЬ 2: Web и API тестирование (вопросы 16–28)

**16. Какой HTTP метод используется для ЧАСТИЧНОГО обновления ресурса?**

a) PUT  
b) POST  
c) PATCH ✅  
d) UPDATE  

> **Ответ: C.** PATCH — частичное обновление (только переданные поля). PUT — полная замена объекта (непереданные поля обнуляются).

---

**17. Что вернёт сервер при обращении к несуществующему ресурсу?**

a) 200  
b) 400  
c) 404 ✅  
d) 500  

> **Ответ: C.** 404 Not Found — ресурс не найден. 400 — неверный запрос (неправильные данные). 500 — внутренняя ошибка сервера.

---

**18. Запрос выполнен, но у пользователя нет прав на ресурс. Какой статус-код?**

a) 401 Unauthorized  
b) 403 Forbidden ✅  
c) 404 Not Found  
d) 400 Bad Request  

> **Ответ: B.** 403 Forbidden — аутентифицирован (известен), но нет прав. 401 Unauthorized — не аутентифицирован вообще (нужно залогиниться).

---

**19. В Postman где настраивают разные URL для dev/staging/prod?**

a) Headers  
b) Pre-request Scripts  
c) Environments ✅  
d) Collections  

> **Ответ: C.** Environments в Postman — наборы переменных (base_url, token и т.д.) для разных окружений. Переключение без изменения запросов.

---

**20. Что такое JWT токен?**

a) Тип HTTP запроса  
b) Формат данных, альтернатива JSON  
c) Токен из трёх частей: Header.Payload.Signature, закодированных Base64 ✅  
d) Протокол авторизации  

> **Ответ: C.** JWT (JSON Web Token) = Header (алгоритм) + Payload (данные пользователя) + Signature (подпись). Передаётся в заголовке: `Authorization: Bearer eyJ...`

---

**21. Что такое Cross-Site Scripting (XSS)?**

a) Кража cookies через SQL  
b) Внедрение вредоносного JavaScript в страницу через пользовательский ввод ✅  
c) Подделка HTTP запросов  
d) Перехват трафика  

> **Ответ: B.** XSS — атака внедрением JS кода (например в поле ввода). Manual QA проверяет: `<script>alert(1)</script>` в полях. Сервер должен экранировать вывод.

---

**22. Что такое IDOR?**

a) Протокол обмена данными  
b) Insecure Direct Object Reference — доступ к чужим данным через подмену ID в запросе ✅  
c) Тип SQL инъекции  
d) Метод шифрования  

> **Ответ: B.** IDOR — уязвимость: `GET /api/users/123` → меняем на `GET /api/users/124`. Если получили чужие данные — баг безопасности. Нужно проверять авторизацию на уровне ресурса.

---

**23. REST API получил запрос с правильным форматом, но бизнес-логика не позволяет выполнить — какой статус-код?**

a) 400 Bad Request  
b) 404 Not Found  
c) 422 Unprocessable Entity ✅  
d) 500 Internal Server Error  

> **Ответ: C.** 422 — запрос синтаксически корректен, но не может быть выполнен из-за семантических ошибок (например email уже занят при регистрации).

---

**24. Что такое SOA (Service-Oriented Architecture)?**

a) Архитектура с единой БД для всех сервисов  
b) Архитектура где приложение состоит из независимых сервисов, взаимодействующих через стандартные интерфейсы ✅  
c) Трёхуровневая архитектура  
d) Архитектура только для мобильных приложений  

> **Ответ: B.** SOA — разбивка на сервисы с чёткими интерфейсами. Microservices — более мелкая SOA. QA тестирует каждый сервис независимо + интеграцию между ними.

---

**25. Что находится в Application-уровне 3-Tier Architecture?**

a) База данных  
b) Браузер/мобильное приложение  
c) Бизнес-логика, API, серверная обработка ✅  
d) CDN и статические файлы  

> **Ответ: C.** Presentation Tier = UI. **Application Tier** = бизнес-логика, API, обработка запросов. Data Tier = БД.

---

**26. Зачем использовать Charles/Fiddler при тестировании?**

a) Для написания автотестов  
b) Для перехвата и анализа HTTP/HTTPS трафика, подмены ответов ✅  
c) Для проверки производительности  
d) Для управления тест-кейсами  

> **Ответ: B.** Proxy-инструменты позволяют видеть все запросы, изменять их на лету, имитировать медленное соединение, подменять ответы сервера (mock).

---

**27. Что такое Content-Type заголовок в HTTP ответе?**

a) Размер ответа в байтах  
b) Тип данных в теле запроса/ответа (например application/json) ✅  
c) Версия HTTP протокола  
d) Метод кэширования  

> **Ответ: B.** `Content-Type: application/json` — тело является JSON. `Content-Type: text/html` — HTML страница. Важно проверять при тестировании API.

---

**28. Что такое Idempotent HTTP метод?**

a) Метод который работает только с авторизацией  
b) Метод повторное выполнение которого даёт тот же результат что и однократное ✅  
c) Метод который не возвращает тело ответа  
d) Метод только для чтения данных  

> **Ответ: B.** Идемпотентные: GET, PUT, DELETE. Не идемпотентные: POST (создаёт новую запись каждый раз), PATCH.

## 📱 ЧАСТЬ 3: Mobile и DB (вопросы 29–36)

**29. iOS Simulator отличается от Android Emulator тем, что:**

a) Simulator работает на Windows  
b) Simulator запускается только на macOS и симулирует поведение, не эмулируя железо ✅  
c) Simulator медленнее Emulator  
d) Simulator поддерживает все аппаратные функции  

> **Ответ: B.** iOS Simulator — только macOS, симулирует поведение (не эмулирует chip). Быстрый, но ограниченный. Android Emulator — эмулирует реальное ARM железо, медленнее.

---

**30. Какая команда ADB показывает все логи Android устройства?**

a) `adb debug`  
b) `adb logs`  
c) `adb logcat` ✅  
d) `adb monitor`  

> **Ответ: C.** `adb logcat` — вывод всех логов. Фильтрация: `adb logcat -s "TAG"` или `adb logcat *:E` (только ошибки).

---

**31. В чём разница Native и Hybrid мобильного приложения?**

a) Native только для iOS, Hybrid только для Android  
b) Native написано на нативном языке платформы, Hybrid — веб-технологии в нативной оболочке ✅  
c) Hybrid всегда быстрее Native  
d) Native нельзя опубликовать в App Store  

> **Ответ: B.** Native: Swift/ObjC (iOS), Kotlin/Java (Android) — лучший UX. Hybrid: React Native, Ionic — одна кодовая база для двух платформ.

---

**32. Какой SQL запрос вернёт пользователей БЕЗ заказов?**

a) `SELECT * FROM users INNER JOIN orders ON users.id = orders.user_id`  
b) `SELECT * FROM users WHERE orders = NULL`  
c) `SELECT u.* FROM users u LEFT JOIN orders o ON u.id = o.user_id WHERE o.id IS NULL` ✅  
d) `SELECT * FROM users EXCEPT SELECT * FROM orders`  

> **Ответ: C.** LEFT JOIN возвращает всех пользователей + NULL для orders если заказов нет. WHERE o.id IS NULL фильтрует только тех у кого нет заказов.

---

**33. В чём особенность INNER JOIN?**

a) Возвращает все строки из обеих таблиц  
b) Возвращает только строки с совпадением в ОБЕИХ таблицах ✅  
c) Возвращает только строки из левой таблицы  
d) Объединяет таблицы без условия  

> **Ответ: B.** INNER JOIN = пересечение. Если пользователь есть в users, но нет в orders — он не попадёт в результат.

---

**34. Что нужно проверить в БД после POST запроса (создание пользователя)?**

a) Только статус-код ответа  
b) Что запись появилась в таблице users с правильными данными, правильным timestamps, ID ✅  
c) Ничего, API тест достаточен  
d) Только что запись уникальна  

> **Ответ: B.** DB verification после CRUD — важная часть API тестирования. Проверяем: запись создана, все поля правильны, NOT NULL поля не пустые, Foreign Keys корректны.

---

**35. Что такое MongoDB Document?**

a) Текстовый файл с настройками  
b) JSON-подобная структура данных, аналог строки в реляционной БД ✅  
c) Тип индекса в MongoDB  
d) Метод авторизации  

> **Ответ: B.** MongoDB: Document (строка) → Collection (таблица) → Database. Документ хранит данные в BSON формате (Binary JSON).

---

**36. Что такое SQL Injection?**

a) Инъекция JavaScript в HTML  
b) Атака через вставку вредоносного SQL кода в поля ввода ✅  
c) Тип XSS атаки  
d) Метод оптимизации SQL запросов  

> **Ответ: B.** SQL Injection: вводим `' OR 1=1 --` в поле логина → если не защищено, запрос ломается и возвращает все записи. Manual QA проверяет базовые инъекции в каждом текстовом поле.

## ⚡ ЧАСТЬ 4: Performance и инструменты (вопросы 37–40)

**37. Цель Stability (Soak) Testing?**

a) Проверка системы при максимальной нагрузке  
b) Проверка поведения при нормальной нагрузке в течение длительного времени для обнаружения Memory Leaks ✅  
c) Тестирование при резком скачке нагрузки  
d) Проверка конфигурации сервера  

> **Ответ: B.** Soak Testing — 8-24 часа под нормальной нагрузкой. Ищем: утечки памяти, деградацию производительности, переполнение логов, connection pool exhaustion.

---

**38. Что такое Error Rate в performance тестировании?**

a) Количество ошибок в коде  
b) % запросов завершившихся ошибкой (4xx/5xx) от общего числа ✅  
c) Частота возникновения багов  
d) Скорость обработки ошибок  

> **Ответ: B.** Error Rate = (ошибочные ответы / все ответы) × 100%. Приемлемый уровень: <1%. Высокий Error Rate при нагрузке = проблема масштабируемости.

---

**39. Какой инструмент используется для нагрузочного тестирования?**

a) Postman  
b) Selenium  
c) JMeter ✅  
d) Charles Proxy  

> **Ответ: C.** Apache JMeter — самый популярный open-source инструмент нагрузочного тестирования. Также: k6, Gatling, Locust, Artillery.

---

**40. Что означает команда `docker-compose up -d`?**

a) Удалить все Docker контейнеры  
b) Скачать Docker образ  
c) Запустить все сервисы из docker-compose.yml в фоновом режиме ✅  
d) Показать статус контейнеров  

> **Ответ: C.** `docker-compose up -d` — запускает все сервисы описанные в docker-compose.yml в detached (фоновом) режиме. `docker ps` — посмотреть запущенные контейнеры.
