## Кратко

- `DHCP Snooping` защищает сеть от rogue DHCP server.
- DHCP по умолчанию доверчив: клиент принимает ответ от того сервера, который ответил.
- Коммутатор с `DHCP Snooping` разрешает DHCP offer только с доверенных портов.
- Пользовательские access-порты обычно остаются untrusted.
- Trusted-порты - это uplink или порт в сторону настоящего DHCP server.
- Если забыть доверенный порт на пути ответа, клиенты перестанут получать адреса.
- Binding table от `DHCP Snooping` потом используют другие функции защиты Layer 2.

## Главное

- Вопрос не в том, где находится клиент, а в том, откуда приходит легитимный DHCP offer.
- Нельзя доверять порт только потому, что к нему подключен пользователь, которому нужен адрес.
- Trust boundary должен совпадать с реальным путем DHCP-ответов.
- В сети с несколькими switch доверенные uplink-порты нужно настроить на каждом hop.
- Если доверять все порты подряд, функция теряет смысл.
- `DHCP Snooping` - не отдельная галочка, а основа для последующих защит, например проверок IP-to-MAC.

## Заметки

`DHCP Snooping` звучит как странное название, но сама функция очень практичная. DHCP работает тихо, пока не ломается. Пользователь включает устройство, оно отправляет broadcast-запрос, сервер отвечает, устройство получает IP-адрес, gateway, DNS и начинает работать.

Проблема в том, что DHCP не умеет сам определить, кто настоящий сервер. Если в сети появится другое устройство, которое тоже начнет отвечать на DHCP-запросы, клиенты могут принять его ответ.

Иногда это случайность. Кто-то принес домашний router, подключил его в офисную сеть, а на нем включен DHCP. Клиенты получают неправильные адреса или неправильный gateway и пропадают из сети.

Иногда это атака. Rogue DHCP server может выдавать адреса из правильной подсети, но указывать себя как default gateway. Тогда пользователю кажется, что сеть работает, но трафик проходит через чужое устройство. Это уже man-in-the-middle.

## Проблема Rogue DHCP

Представим NetworkChuck Coffee.

Есть настоящий DHCP server. Он выдает адреса для кафе, админской сети и других VLAN. Все работает нормально.

Потом кто-то подключает устройство, которое тоже начинает раздавать DHCP:

- домашний router;
- маленький lab-сервер;
- rogue access point;
- неправильно настроенный laptop;
- устройство атакующего.

Клиент не спрашивает: "Ты точно настоящий DHCP server?" Он просто ждет ответ.

Если rogue DHCP ответит быстрее, клиент может получить:

- неправильный IP-адрес;
- неправильный default gateway;
- неправильный DNS server;
- маршрут через атакующего;
- настройки, которые ломают доступ к сети.

Это опасно именно потому, что проблема может выглядеть как обычный сбой DHCP, а не как атака.

## Что делает DHCP Snooping

`DHCP Snooping` говорит коммутатору:

```text
DHCP offer можно принимать только с портов, которым я явно доверяю.
```

После включения функции все порты считаются untrusted, пока ты сам не настроишь доверие.

Логика такая:

| Тип порта | Поведение |
| --- | --- |
| `trusted` | Может принимать DHCP server replies. |
| `untrusted` | DHCP server replies блокируются. |

Клиентские DHCP-запросы с access-портов проходят. Это нормально. Но ответы DHCP server должны приходить только через проверенный путь.

Главный вопрос при настройке:

```text
Через какой интерфейс этот switch получает легитимный DHCP offer?
```

Именно этот интерфейс обычно должен быть trusted.

## Базовая настройка

Пример:

```text
ip dhcp snooping
ip dhcp snooping vlan 10,20

interface gi0/1
 ip dhcp snooping trust
```

Разбор:

| Команда | Что означает |
| --- | --- |
| `ip dhcp snooping` | Включает функцию глобально. |
| `ip dhcp snooping vlan 10,20` | Включает защиту для VLAN 10 и VLAN 20. |
| `ip dhcp snooping trust` | Помечает интерфейс как доверенный для DHCP-ответов. |

Все остальные порты остаются untrusted, если явно не настроено иначе.

## Где ставить trust

Самая частая ошибка - доверять порт пользователя, потому что пользователь должен получить DHCP-адрес.

Это наоборот.

Доверять нужно не клиента, а направление, откуда приходит DHCP offer.

Примеры:

| Сценарий | Как думать |
| --- | --- |
| DHCP server подключен прямо к switch | Trusted - порт к DHCP server. |
| DHCP server за router | Trusted - uplink к router. |
| DHCP server за другим switch | Trusted - trunk/uplink в сторону DHCP server. |
| Access-порт пользователя | Обычно untrusted. |

В сети с несколькими коммутаторами нужно проверить весь путь. Если DHCP offer проходит через три switch, каждый switch должен доверять правильный uplink, через который этот ответ приходит.

Один пропущенный `ip dhcp snooping trust` - и клиенты за этим участком могут перестать получать адреса.

## Симулятор и реальные устройства

В лабораториях `Packet Tracer` с `DHCP Snooping` иногда ведет себя странно, особенно вместе с VLAN. Это не лучший источник для выводов о реальной production-настройке.

На реальном оборудовании логика проще:

- включи `DHCP Snooping`;
- укажи VLAN;
- доверь только порты, через которые приходят легитимные DHCP-ответы;
- не доверяй access-порты пользователей;
- проверь работу show-командами.

Если в симуляторе приходится доверять лишние интерфейсы, чтобы демонстрация заработала, не переноси эту привычку в реальную сеть. Доверить все порты - значит отключить смысл защиты.

## Таблица привязок

Важный бонус `DHCP Snooping` - binding table.

Коммутатор запоминает, какой MAC-адрес получил какой IP-адрес, в какой VLAN и на каком интерфейсе.

Упрощенно:

```text
MAC address + IP address + VLAN + interface
```

Это полезно не только для DHCP. Другие функции защиты Layer 2 могут использовать эту таблицу, чтобы проверять, не пытается ли устройство притвориться чужим IP-адресом.

Именно поэтому `DHCP Snooping` часто идет перед более сильными механизмами вроде `Dynamic ARP Inspection`.

## Проверка

Полезные команды:

```text
show ip dhcp snooping
show ip dhcp snooping binding
show interfaces trunk
show running-config | include dhcp snooping
```

Что смотреть:

- включен ли `DHCP Snooping` глобально;
- включен ли он на нужных VLAN;
- какие порты trusted;
- не доверены ли лишние access-порты;
- появилась ли binding table;
- совпадает ли trunk/VLAN-путь с реальным путем DHCP.

Если клиенты не получают адреса, сначала проверь не DHCP server, а trust boundary. Очень часто сервер исправен, а проблема в одном uplink, который забыли сделать trusted.

## Сценарий NetworkChuck Coffee

В NetworkChuck Coffee клиенты и сотрудники должны получать адреса от настоящего DHCP server.

Мы хотим:

- разрешить DHCP-запросы от клиентов;
- разрешить DHCP-ответы только со стороны настоящей инфраструктуры;
- заблокировать rogue DHCP server на access-порту;
- сохранить binding table для будущих защит.

Это дает простой результат: случайная коробка, подключенная в розетку, не сможет начать раздавать сетевые настройки всему кафе.

## Главный вывод

`DHCP Snooping` - это про границы доверия.

Ты явно говоришь switch, какие интерфейсы имеют право приносить DHCP-ответы. Все остальные порты считаются подозрительными для server-side DHCP-трафика.

Функция небольшая, но эффект большой: меньше риска rogue DHCP, меньше шансов на man-in-the-middle через поддельный gateway и больше данных для дальнейшей защиты Layer 2.

## Команды и термины

| Термин | Значение |
| --- | --- |
| `DHCP Snooping` | Функция switch, фильтрующая DHCP-ответы по trusted/untrusted портам. |
| rogue DHCP server | Неавторизованный DHCP server в сети. |
| `trusted port` | Порт, которому разрешено принимать DHCP server replies. |
| `untrusted port` | Порт, на котором DHCP server replies блокируются. |
| DHCP offer | Ответ DHCP server с предложением сетевых настроек. |
| binding table | Таблица соответствий MAC, IP, VLAN и interface, построенная через DHCP. |
| trust boundary | Граница, где switch явно доверяет инфраструктурному DHCP-трафику. |
| man-in-the-middle | Сценарий, где атакующий пропускает трафик через себя. |

## Вопросы

### 1. Что блокирует DHCP Snooping?

Ответ: DHCP-ответы от неавторизованных портов.

### 2. Почему access-порт пользователя обычно не должен быть trusted?

Ответ: Пользовательский порт должен отправлять DHCP-запросы, но не должен приносить DHCP-ответы как сервер.

### 3. Что случится, если забыть trusted uplink на пути DHCP offer?

Ответ: Клиенты за этим участком могут перестать получать IP-адреса.

### 4. Зачем нужна binding table?

Ответ: Она показывает соответствие MAC, IP, VLAN и interface и может использоваться другими функциями защиты.

### 5. Почему нельзя просто доверить все порты?

Ответ: Тогда rogue DHCP server тоже сможет отправлять DHCP-ответы, и защита потеряет смысл.
